# Live EEZ integration tests

One CI workflow uses separate Rollup0 and RollupX jobs. Each builds the candidate with the repository Dockerfile and runs the selected upstream Kurtosis scenario driver with the candidate Nethermind follower. It checks the complete settled prefix, raw transactions, receipts and native accounting. It restarts Nethermind with its existing database, then adds a new follower with an empty independent database.

At run start, CI resolves upstream main once and reads its Core gitlink. The Rollup0 live lane requires a streaming composer. Before PR206 reaches main, it uses the exact reviewed public commit `30e6a1fc319d1bf02a4251dbbee240cefcf9310c`. A changed PR head requires review. After merge, current main is selected automatically. The source and runtime artifact must match this exact revision. Results retain source revisions, artifact digest, binary checksums, candidate revision and runtime tool versions. An explicit upstream revision permits replay; it must belong to upstream main history or be the exact reviewed streaming commit. A missing matching artifact causes a build of the selected source, not a fallback to an older successful revision.

The temporary upstream overlay adds the Nethermind service and observations after the upstream scenario scripts. It keeps the current upstream driver, contracts, scenarios and assertions. For the native static-counter evidence writer, large causal and blob JSON objects are read from their existing files instead of OS command-line arguments. JSON values, validation assertions and evidence fields remain unchanged; unexpected output boundaries fail explicitly. New upstream tests are therefore consumed without manual source pin updates. A changed integration boundary fails explicitly.

The Rollup0 live lane verifies the **Rollup0 0x76 follower profile** with the candidate Nethermind `prove.v2` attester. The existing signer service name, port, deployment arguments and upstream assertions remain. The public deployment key is imported through stdin into an encrypted keystore; its address must match the deployed signer. The unchanged state-chaining tests correlate the signed height and digest with composer attestation and accepted L1 settlement. The signer outage test requires no settlement while the candidate is stopped and progress after restart.

The published composer has no client-certificate configuration. An isolated CI-only HAProxy frontend accepts the exact `prove.v2.Prover/ProveStream` method and forwards HTTP/2 to the candidate through mutual TLS. It verifies the server certificate and hostname and uses the pinned composer certificate. It does not change frames. The frontend blocks `prove.v1`, and the candidate v1 listener remains loopback-only. A fallback cannot pass this lane.

The explicit `rollup0-conditional` profile fully validates execution and settlement from the selected parent, then signs the recomputed public-input digest. It does not assert prior L1 acceptance of that parent. This follows the published Rollup0 streaming implementation. The composer can retain mined proofs in its input; the profile ignores those bounded canonical proof fields and always issues a fresh validated signature. This is an explicit compatibility difference from the common spec's proofless-input wording. Requests, responses and proof oracles remain unchanged. Authenticated `rollup0-calldata` and `rollupx-native` retain their authorization and proofless gates.

Live `prove.v2` Resume/Rewind/Cancel coverage remains limited to controls that the upstream scenarios actually trigger. Raw conformance replays test those controls separately. RollupX and draft Rollup0 0x45 require their own profiles and tests.

Results use an exact canonical L1 registry snapshot. The registered commitment is an L2 block hash. Both nodes must provide its entire ancestry and the same transaction bytes and receipts. Canonical L1 and L2 endpoints are checked again after observations. Missing data, empty required scenarios and any mismatch fail the lane.

The initial observation verifies zero native account balance and nonce at genesis on both nodes. Later observations reuse that passed result only when both nodes still have the same genesis hash, state root and chain ID. They do not require historical genesis state to remain available. Account state at the settled endpoint is still checked on both nodes in every phase.

PRs and pushes touching EEZ or its execution dependencies start the workflow. The daily schedule detects upstream-only changes after the workflow reaches the default branch. Manual runs can select an exact upstream revision.

The result records the candidate prover image ID, candidate revision and nonzero signed-window/remote-attestation counts in `candidate-prover.json`. The upstream image build is skipped through its existing switch; an image ID change fails the lane. It also requires every signed-window record to name `prove.v2` and match the upstream count. This proves only the selected Rollup0 profile and scenarios that actually run.

All nodes and Docker builds run on disposable CI runners. Cleanup removes only this run's named enclave and candidate images. Existing VM services are not used or modified.

The candidate follower and prover use the same execution settings, frozen from the selected source's executor factory. The reviewed PR206 source uses `EthBlockExecutorFactory`, so consensus-layer calls remain active. Sources with `EezBlockExecutorFactory` omit beacon-root and consensus-request transitions; EIP-2935 remains active. An unknown executor fails source selection. These settings are trusted startup configuration. Upstream genesis, requests and expected outputs remain unchanged.

The RollupX lane selects current public RollupX main and its Core gitlink. It builds the selected upstream binaries in the upstream-declared Debian Rust image, retains their checksums and packages them in a CI runtime image. The original upstream contracts, native blob scenarios, prover and scenario assertions remain. The Nethermind follower uses the deployment-generated RollupX genesis, canonical L1 RPC and the same real beacon endpoint for initial derivation, restart and fresh recovery. Observations compare the full settled ancestry, transaction bytes and receipts and require nonzero native activity.

This lane tests the candidate **RollupX follower with the upstream prover**. Its separate `candidate-follower.json` report never claims the upstream signatures came from Nethermind. The currently published RollupX composer calls `prove.v1`. The native Nethermind prover also accepts inline-window v1, but does not yet implement the preparation/cache operations and implementation identity agreement required by that composer. Direct composer/candidate-prover interoperability remains a separate gate. The existing Rollup0 candidate-prover evidence checks stay mandatory and unchanged.
