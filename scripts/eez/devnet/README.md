# Live EEZ integration tests

One CI workflow builds the Nethermind follower and prover images once. Reusable preparation and test workflows keep each profile independent. Preparation runs alongside the common candidate build. Rollup0 does not wait for RollupX preparation, or vice versa. Each producer freezes upstream/Core revisions and prepares runtime binaries, contract artifacts, deploy images and Rust test executables. Test jobs download these same-run artifacts and execute separate suites in parallel. They do not compile Rust or Nethermind. Archives preserve executable modes. Producer artifact names use the run ID so failed-job reruns can reuse successful builds. A standard Actions cache reuses prepared upstream inputs for the selected repository/profile, source/Core revisions, execution settings and adapter/build files. Resolution-only metadata, such as the current upstream main and the selection origin of the same source, does not change the key. Fresh resolution metadata stays outside the cached payload. On a hit, preparation verifies the build identity and combines the current resolution with the cached runtime provenance and binary checksums. A new selected upstream revision or adapter change causes a rebuild. Candidate Nethermind images are still built from the current commit.

The RollupX protocol job has a 20-minute limit, including setup, and an 18-minute upstream execution budget. Every other test job has a 15-minute limit, including setup. Cold build producers have separate limits and can take longer. The limit is a failure boundary; successful CI timings are required before claiming that every partition fits. The final job requires all 19 partitions, matching source manifests, wave prerequisites and complete protocol assignment. A partial job cannot report a complete suite.

Each of the 12 live partitions uses its own runner and fresh Kurtosis enclave with the candidate Nethermind follower. Build artifacts and images are shared. The six embedded jobs start their own test nodes; the contract job needs no devnet. Live partitions compare the complete settled prefix, raw transactions, receipts and native accounting.

The outer CI wrapper owns enclave teardown after all upstream and candidate checks. The adapter removes only the upstream cleanup's final `stop.sh` call, with an exact boundary guard. Upstream process cancellation, diagnostics, result validation and failure status remain. This avoids a second enclave removal inside the 13-minute upstream execution deadline. CI selects Kurtosis's standard Vector log collector before starting the engine, avoiding repeated optional OTel startup attempts. Service logs and test assertions remain enabled. Test deadlines remain unchanged.

One protocol job per profile runs the entire discovered eligible suite on one devnet. Rollup0 keeps its upstream sequential runner. RollupX uses its upstream runner with at most eight concurrent scenarios. That runner owns worker wallets, checkout locking, output directories and the bridge-before-bridgeL2 dependency. Separate orchestrators never share a devnet or output tree. Full native protocol evidence must report complete suite, receipt, causal and semantic coverage.

The recovery job runs the original inbound and outbound waves in order, then restarts Nethermind with its existing database and adds a fresh follower with an independent database. This also covers both directional waves without two extra devnets. Mixed, mixed-pure and state-chaining jobs each run the original inbound wave first to establish escrow before outbound operations. Their original counts, revert checks and assertions remain. No two wave or fault scripts run concurrently on the same devnet. Ingress and service faults remain separate.

Each consumer derives its coverage plan from the frozen source. Changes to test grouping do not rebuild the cached runtime and fixture images. Rollup0 prepares its existing observation adapters before one Cargo invocation builds the required runtime targets and the seven selected integration test executables. When a matching runtime artifact is available, Cargo builds only the selected integration tests. Both paths keep the same `ci-e2e` profile and locked dependencies. Compiler JSON must identify every exported test as an integration test with its test harness enabled. The producer retains the standard Cargo timing HTML report beside its build records for compilation and linking analysis.

When exact prepared inputs are unavailable, a separate standard Rust cache restores registry/git downloads and compiled dependencies for Rollup0 after toolchain selection. Its key includes the runner OS/architecture, Rust compiler, Cargo configuration, dependency manifests, lockfile and compiler environment, including `LLVM_SYS`. Build-script or source changes can reuse dependencies; Cargo still builds the current workspace and selected integration tests with `--locked`. The cache excludes installed Cargo binaries and does not replace source validation, executable inventory checks or live tests. The first population still requires a cold build. Restore/save costs and warm compilation require CI measurement.

Rollup0 refreshes the relay housekeeper after actual validator registration and requires the builder to load those registrations before the original bundle-inclusion check. This matches the upstream RollupX startup sequence. The deploy image imports the contract artifacts, compiler cache and installed Solidity compiler from preparation. Normal Forge checks validate the imported state instead of forcing a second full compilation. A separate standard Actions cache retains Solidity outputs and compiler metadata by profile, source revision and Foundry version. A matching older revision can seed the compiler cache; both Forge builds still run and validate current source and settings. This cache never replaces exact-source prepared inputs or skips compilation checks. Source files and compiler settings remain unchanged. These changes do not alter slot timing, proof deadlines, scenario inputs or assertions. Successful timing measurements remain required.

At run start, CI resolves upstream main once and reads its Core gitlink. The Rollup0 live lane requires a streaming composer. Before PR206 reaches main, it uses the exact reviewed public commit `d09cd33d92762995227f7de623ba925f420b0367`. This revision uses the current Rollup0 L2 execution factory and preserves newer streaming progress when an older prevalidation arrives. Its client checks that both v1 and v2 attestations bind the requested batch. RPC messages and proof inputs remain unchanged. A changed PR head requires review. After merge, current main is selected automatically. The source and runtime artifact must match this exact revision. Results retain source revisions, artifact digest, binary checksums, candidate revision and runtime tool versions. An explicit upstream revision permits replay; it must belong to upstream main history or be an explicitly reviewed streaming commit. The previous tested commits `0b31df7edbe3e062fffdd18ab31d5911da3b51f3`, `21e0805628f4bd80bcf41c9d2b8f58c179984072`, `32549bff918f5d9ac14ed8a78eace22e5c114d4c` and `30e6a1fc319d1bf02a4251dbbee240cefcf9310c` remain available for explicit replay. The current reviewed client requires bounded pipelining with up to eight outstanding requests. A missing matching artifact causes a build of the selected source, not a fallback to an older successful revision.

The temporary upstream overlay adds the Nethermind service and observations after the upstream scenario scripts. It selects independent driver invocations for each partition and keeps the scenario scripts, contracts and their assertions unchanged. Each partition runs the original readiness and proof-path checks. Its result records only that partition; the original full-suite pass summary is not used. For the native static-counter evidence writer, large causal and blob JSON objects are read from their existing files instead of OS command-line arguments. JSON values, validation assertions and evidence fields remain unchanged; unexpected output boundaries fail explicitly. New upstream tests are therefore consumed without manual source pin updates. A changed integration boundary fails explicitly.

The Rollup0 live lane verifies the **Rollup0 0x76 follower profile** with the candidate Nethermind `prove.v2` attester. The existing signer service name, port, deployment arguments and upstream assertions remain. The public deployment key is imported through stdin into an encrypted keystore; its address must match the deployed signer. The unchanged state-chaining tests correlate the signed height and digest with composer attestation and accepted L1 settlement. The signer outage test requires no settlement while the candidate is stopped and progress after restart.

The published composer has no client-certificate configuration. An isolated CI-only HAProxy frontend accepts the exact `prove.v2.Prover/ProveStream` method and forwards HTTP/2 to the candidate through mutual TLS. It verifies the server certificate and hostname and uses the pinned composer certificate. It does not change frames. The frontend blocks `prove.v1`, and the candidate v1 listener remains loopback-only. A fallback cannot pass this lane.

The explicit `rollup0-conditional` profile fully validates execution and settlement from the selected parent, then signs the recomputed public-input digest. It does not assert prior L1 acceptance of that parent. This follows the published Rollup0 streaming implementation. The composer can retain mined proofs in its input; the profile ignores those bounded canonical proof fields and always issues a fresh validated signature. This is an explicit compatibility difference from the common spec's proofless-input wording. Requests, responses and proof oracles remain unchanged. Authenticated `rollup0-calldata` and `rollupx-native` retain their authorization and proofless gates.

Six separate Rollup0 jobs run the selected upstream `durability`, `resumption`, `resumption_append`, `native_system`, `contract_post` and `partial_consumption` integration suites. The original test bodies and assertions remain. Added observations start an independent Nethermind follower from the same genesis and canonical L1. They verify complete settled prefixes before and after resumption, restart the candidate with its existing database and verify fresh database recovery. They reuse the candidate image and prefix verifier. The producer compiles the Rust targets once, including when CI downloads matching runtime binaries. Consumers retain the upstream executable layout and run the compiled test binaries directly.

The `contract_post` and `partial_consumption` observations require the exact settlement hash from each original scenario to be canonical in both the reference and candidate chain. The full settled-prefix comparison still runs. The contract-post case observes the copied batch and subsequent settlement. The partial-consumption cases observe the mixed prefix and anchor-only settlement. Synchronous helper-oracle tests in these binaries also run unchanged; they do not count as candidate follower observations. Original upstream tracing and blind-follower assertions remain upstream-only checks.

A separate job runs the upstream contract test command from the same source tree and keeps its JSON output. The producer prepares the contract artifacts required by embedded fixtures. Contract-only success is not candidate execution evidence.

The `native_system` suite also observes the candidate after a real deposit, after the second composer settles an outbound transfer, and after fresh database recovery. It checks the original full settled prefix and the expected system and recipient accounting. The original upstream assertions, including its public RPC checks on upstream nodes, remain unchanged. Candidate observations do not claim that those upstream-only RPC checks ran against Nethermind.

These embedded suites use the upstream composer and prover. Their candidate evidence covers the Nethermind follower. `embedded/candidate-coverage.json` records source hashes, candidate image/source identity and observations for each covered case. Other discovered upstream integration cases and the upstream ignored database-ahead-of-L1 regression remain `required_but_missing`. New cases in an adapted suite require candidate observations. This is partial coverage, not complete upstream non-unit or native prover interoperability.

A separate Rollup0 live control probe uses the upstream generated Rust gRPC client against the deployed candidate prover through the same HTTP/2-to-mTLS adapter. It captures two consecutive transaction-empty blocks, raw RLP and execution witnesses from the last 64 settled blocks. Inputs remain bound to the passed follower observation and canonical L1/L2 rechecks. Missing blocks or witnesses fail the job. It checks disconnect/Resume, Rewind/re-execution, pipelined Cancel, rejection of cancelled Resume and an independent session that remains usable. Cancel can retire the queued block before execution; this is not deterministic worker-overlap evidence. The CI prover reserves capacity for four sessions (1 GiB total reservation) so the composer and both control sessions can coexist. Production defaults remain unchanged. The probe does not call Finalize or claim L1 acceptance after each control, and does not claim that the upstream composer sends these controls. Raw conformance and existing live composer settlement remain separate evidence. RollupX and draft Rollup0 0x45 require their own profiles and tests.

Results use an exact canonical L1 registry snapshot. The registered commitment is an L2 block hash. Both nodes must provide its entire ancestry and the same transaction bytes and receipts. Canonical L1 and L2 endpoints are checked again after observations. Missing data, empty required scenarios and any mismatch fail the lane.

Partition jobs check the actual zero native account balance and nonce at genesis before scenario traffic. This capture does not claim settled prefix coverage. They run the full initial prefix check after their selected scenario, followed by the scenario observation. This lets follower startup progress during the scenario. Later observations reuse the passed genesis state only when both nodes still have the same genesis hash, state root and chain ID. Required prefix reports reject genesis-only results. They do not require historical genesis state to remain available. Account state at the settled endpoint is still checked on both nodes in every phase.

PRs and pushes touching EEZ or its execution dependencies start the workflow. The daily schedule detects upstream-only changes after the workflow reaches the default branch. Manual runs can select an exact upstream revision.

The result records the candidate prover image ID, candidate revision and nonzero signed-window/remote-attestation counts in `candidate-prover.json`. The upstream image build is skipped through its existing switch; an image ID change fails the lane. It also requires every signed-window record to name `prove.v2` and match the upstream count. This proves only the selected Rollup0 profile and scenarios that actually run.

All nodes and Docker builds run on disposable CI runners. Cleanup removes only this run's named enclave and candidate images. Existing VM services are not used or modified.

The candidate follower and prover use the same execution settings, frozen from the selected source's executor factory. The reviewed PR206 source uses `EezBlockExecutorFactory`, so beacon-root and consensus-request transitions are omitted. Sources with `EezBlockExecutorFactory` omit beacon-root and consensus-request transitions; EIP-2935 remains active. An unknown executor fails source selection. These settings are trusted startup configuration. Upstream genesis, requests and expected outputs remain unchanged.

The RollupX lane selects current public RollupX main and its Core gitlink. It first looks for a published runtime from a successful upstream main push at the exact selected revision. The upstream payload helpers validate the immutable digest, source and Core revisions, Cargo.lock hash, platform, archive checksum, seven binaries and published image identities. Missing published payloads fall back to a source build in the upstream-declared Debian Rust image. Validation failures stop the job. Results retain the selected source, immutable payload reference, binary checksums and tool versions. The binaries are packaged in a CI runtime image. The original upstream contracts, native blob scenarios, prover and scenario assertions remain. The Nethermind follower uses the deployment-generated RollupX genesis, canonical L1 RPC and the same real beacon endpoint for initial derivation, restart and fresh recovery. Observations compare the full settled ancestry, transaction bytes and receipts and require nonzero native activity.

This lane tests the candidate **RollupX follower with the upstream prover**. Its separate `candidate-follower.json` report never claims the upstream signatures came from Nethermind. The currently published RollupX composer calls `prove.v1`. The native Nethermind prover also accepts inline-window v1, and implements preparation/cache operations. The composer still requires its implementation-specific validation identity. A shared identity contract remains a separate upstream gate. Direct composer/candidate-prover interoperability remains a separate gate. The existing Rollup0 candidate-prover evidence checks stay mandatory and unchanged.
