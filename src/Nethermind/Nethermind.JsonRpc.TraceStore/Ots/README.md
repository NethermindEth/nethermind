# OTS account history

TraceStore provides a partial Otterscan API:

- `ots_getApiLevel` returns **0**, not a claim of full Otterscan compatibility.
- `ots_searchTransactionsBefore(address, blockNumber, pageSize)`
- `ots_searchTransactionsAfter(address, blockNumber, pageSize)`
- `ots_traceTransaction(transactionHash)`
- `ots_getTransactionError(transactionHash)`
- `ots_getInternalOperations(transactionHash)`
- `ots_hasCode(address, block)`
- `ots_getTransactionBySenderAndNonce(sender, nonce)`
- `ots_getContractCreator(address)`

Enable `TraceStore.Enabled`, include `Trace` in `TraceStore.TraceTypes`, and explicitly add `Ots` to `JsonRpc.EnabledModules`. Retain receipts (`Receipt.StoreReceipts`) and transaction lookup history (`Receipt.TxLookupLimit = 0` for unrestricted lookup). Set `TraceStore.BlocksToKeep = 0` to retain traces indefinitely; this does not backfill traces for blocks processed before TraceStore was enabled. Historical queries require the corresponding canonical block bodies, stored traces and receipts. History searches and transaction tracing do not require historical state; missing receipts are reported as unavailable, never regenerated by re-executing blocks. Code queries require state at the selected block. Contract-creator queries require current state and complete canonical stored creation history.

## Search semantics

Block cursors are exclusive. A before cursor of zero starts at the head; an after cursor of zero starts after genesis. Page sizes range from 1 to 25 transactions, but all matches in the final matching block are included, so a page can exceed the requested size. Results are ordered by descending block number and transaction index, with corresponding receipts in the same order. Receipt timestamps are decimal numbers.

Search matches senders, destinations and created addresses anywhere in the stored transaction call tree, including zero-value and reverted calls. Each matching transaction appears once. Logs alone and block rewards do not count as call involvement. These results describe calls, not committed ETH transfers.

A further matching block is read to determine whether another page exists. `firstPage` identifies the newest end and `lastPage` the oldest end of the result history. When paging backwards, use the oldest returned block as the next cursor; when paging forwards, use the newest returned block.

## Additional queries

`ots_getTransactionError` returns the root transaction's raw REVERT bytes, not a nested call's revert data. The top-level recorded output is authoritative, including an explicitly empty output; the root action's output is a fallback only when the top-level output is absent. Success and exceptional halts return `0x`. Missing recorded revert output is an error rather than an invented empty reason; the transaction is not re-executed.

`ots_getInternalOperations` omits the root transaction, includes nonzero nested CALL transfers and all nested CREATE, CREATE2 and SELFDESTRUCT operations, and preserves execution order. Its numeric operation types are 0, 2, 3 and 1 respectively. Like the reference Otterscan tracer, it retains reverted operations; it does not describe committed balance changes. Missing operation addresses and unsupported creation methods are errors. Stored Parity traces may lack destinations for failed creations, so not every transaction can be served by this backend.

`ots_hasCode` reads account metadata without loading bytecode. It accepts the standard block parameter, including historical blocks, requires canonical executed state even for hash selectors, and resolves `pending` to the executed head like the reference client. Unavailable state is an error. `ots_getTransactionBySenderAndNonce` scans canonical blocks backwards, recovering missing senders from complete receipts whose transaction positions and block identities have been validated, and returns a transaction hash or null. Missing blocks or sender metadata are errors.

`ots_getContractCreator` first checks code at the current head, then scans stored creation traces backwards. It returns the creation transaction hash and immediate creator (the factory, not the originating EOA), ignoring creations under reverted ancestors. Addresses with no current code return null, including destroyed contracts. EIP-6780 selfdestructs that retain code retain the original creator; an actual destruction followed by successful recreation selects the newest extant incarnation. Code present at genesis has no creation transaction to return. EIP-7702 delegation is not a CREATE operation and returns null without scanning creation history; on EIP-7702 chains missing current bytecode is an error because delegation cannot otherwise be distinguished. Successful stored creations without a recorded destination are errors unless a root init destination can be reconstructed from the transaction. Both history scans are timeout-bounded and detect canonical-chain changes; they do not require an external index.

The implementation follows the [official OTS specification](https://github.com/otterscan/execution-apis/blob/b1472414498ccf5e182cca319addc526566a4732/src/ots/otterscan.yaml) and [official book](https://github.com/otterscan/otterscan-book/blob/949235c2e2da1b8adcd1f5f4068bd2021df32a18/src/api-docs/ots-api.md). Nine stable method names are exposed, but block details and transaction pages are not implemented and backend limitations prevent a full compatibility claim, so the API level remains zero. Experimental `ots2` methods are not exposed.

## Traces and limitations

Transaction traces are depth-first call-tree entries, including creations and selfdestructs but excluding precompile entries. Nested creations rejected by balance or call-depth prechecks have no destination and are omitted rather than assigned an invented address. Failed top-level creation destinations are reconstructed from the sender and transaction nonce. Reverted calls are included. `STATICCALL` and `DELEGATECALL` have a null value; creation output contains deployed code.

Precompile account history is unsupported: stored Parity call trees omit nested zero-value precompile calls. A search returns `ResourceUnavailable` if the requested address is an active precompile in any scanned block, rather than certifying an incomplete page. Classification uses each scanned block's fork rules; searches confined to blocks before an address becomes a precompile remain supported.

By default, searches scan blocks and deserialize stored traces without an address index. The initial Otterscan query for an address with at most 25 matching transactions, and any terminal page, must scan to genesis or head to establish the end of history. This common case is generally impractical on long chains without an address index and can occupy all bounded module instances until `JsonRpc.Timeout`. `TraceStore.OtsModuleConcurrentInstances` defaults to 2 (minimum 1); raising it allows more concurrent OTS requests but increases scan CPU, I/O and memory load independently of the live Trace module limit. There is no guarantee that an arbitrary historical search completes within that timeout.

Missing or inconsistent traces, blocks or required receipts produce errors rather than incomplete pages or a false end-of-history indication. Empty blocks do not require stored transaction traces. Canonical-chain changes detected during a request also produce an error; retry the request. An unknown transaction produces a not-found error.

## Optional address index

`TraceStore.AddressIndexEnabled` defaults to `false`. Enabling it requires `TraceStore.BlocksToKeep = 0` and `TraceStore.TraceTypes` including `Trace`. A background builder yields between productive groups of at most 64 blocks and waits one second only when caught up or paused. It reads existing stored traces into a separate `traceAddressIndex` database; it does not backfill missing traces or change the trace store or event-log index.

`TraceStore.AddressIndexFromBlock` is inclusive and defaults to `1`; it must be positive. `TraceStore.AddressIndexLag` is measured in blocks behind the head, defaults to `64`, and must be nonnegative. This lag is not a finality guarantee. Missing or inconsistent source history pauses construction without certifying that block. Earlier history, the recent tail and other history outside certified coverage use the stored-trace scan. Covered candidate blocks still require their canonical bodies, authoritative traces and receipts. Covered negative routing trusts the certified postings; it does not reread unselected trace blobs to detect later mutations. Addresses classified as precompiles at genesis, head or any configured fork bypass acceleration so skipped blocks cannot hide unsupported precompile involvement; the scan still applies each block's fork rules.

A changed canonical checkpoint, repaired database, or missing or inconsistent checkpoint disables indexing and falls back to scanning. A chain change detected during a request returns an error rather than a mixed page. To rebuild an invalid index, restart once with `TraceStore.AddressIndexReset = true`, then set it back to `false`. Reset clears only the separate address-index database, not stored traces. Changing the configured start also requires rebuilding the index. Indexes built with the earlier v2 checkpoint must be rebuilt: the v3 postings also include reconstructed failed top-level creation destinations.

## Experimental position sidecar

The AppContext switch `Nethermind.Experimental.OtsPositionSidecarP1` defaults to off. It enables bounded transaction-position proofs in the address-index metadata namespace; it is experimental, not a stable TraceStore configuration option. It requires the address index and the built-in `ParityLikeTraceSerializer`. It cannot be enabled together with `TraceStore.AddressIndexReset = true`; disable the switch when resetting the address index, then clear the reset flag before enabling it again.

The namespace schema includes explicit record and serializer-format versions, genesis, the configured start and maximum trace depth. Unrelated binary rebuilds and runtime patches do not change it; incompatible stored-trace interpretation changes require bumping the serializer-format version. Earlier assembly/runtime-fingerprinted namespaces remain incompatible and require an explicit rebuild; they are never silently reused. An incompatible fingerprint or orphan namespace disables sidecar use rather than overwriting it. A runtime JSON-options identity change also disables proof use. Missing or unsupported proofs fall back to authoritative stored-trace matching. Blocks exceeding the sidecar's construction limits receive no proof and use the same fallback. Selected malformed proofs or mismatched trace blobs and transaction identities return errors rather than silently omitting matches. The sidecar does not change negative address-index routing or the existing requirements for receipts and canonical bodies.
