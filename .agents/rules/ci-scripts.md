# CI scripts

- Prefer C# file-based apps for new CI automation and substantive additions to migrated tooling. Use top-level statements, `var`, `using var`, and small local functions; share implementation through `#:include` when needed. Apply the same style to script tests and helpers.
- Keep straightforward ports close to the original script's structure and size. Do not turn a short check into an application framework: avoid pass-through wrappers, redundant catch/rethrow layers, and classes or dependency injection added only to make simple code testable.
- Preserve and port existing script test suites. When the original script had no tests, do not add committed tests or a test harness as part of its migration; use local fixtures outside the repository to validate equivalence. A script that is already a repository check needs a direct port, not another harness testing the check itself. Parameterize related cases in existing suites and reuse setup.
- Reuse existing process helpers when their behavior fits; do not copy launch, stream-draining, cancellation, or cleanup plumbing into every script. Introduce included helpers for actual reuse, not to split a tiny script into an entrypoint and a forwarding layer.
- Apply normal performance practices to scripts: use `[GeneratedRegex]` partial methods for fixed patterns, preserving regex options, culture and timeouts. Keep declarations in the owning file; do not add a helper file solely for regexes. Use runtime regexes only for genuinely dynamic patterns, and avoid constructing them repeatedly inside loops.
- Before opening a PR, compare the replacement's implementation and test footprint with the originals. Remove unnecessary scaffolding and explain substantial growth through concrete behavior or regression coverage. Reduce complexity rather than compressing formatting or dropping error handling, cleanup, or meaningful tests.
- Run apps with `dotnet run --file path/to/Script.cs -- arguments` after setting up the required SDK. Use a prebuilt executable when an SDK is unavailable; do not add SDK dependencies to container entrypoints or pre-runtime bootstrap solely to follow this preference.
- Keep simple workflow command invocations in their existing shell. Use another language when an integration/bootstrap environment requires it or the user requests it. This preference does not authorize unrelated rewrites of `scripts/build/`, Dockerfiles, container entrypoints, package hooks, application JavaScript, or developer utilities.
- Preserve command arguments, exit codes, output formats, working directories, and environment propagation when migrating scripts. A C# subprocess cannot modify its parent's environment like a sourced shell file; use explicit state and GitHub output/environment files.
- Name new CI entry points in PascalCase, executable script tests `Test*.cs`, and included helpers `*.Helpers.cs`. Run mixed suites with `dotnet run --file scripts/ci/RunScriptTests.cs -- scripts/<suite>`. Each C# test executable must report test names and finish with `Passed N tests.` (N greater than zero); failures must return a nonzero exit code.
- Validate changed file-based apps with `dotnet run --file scripts/ci/RunScriptTests.cs -- --check path/to/Script.cs`. Keep unused-import checks enabled for entry points and included helpers.
- Directory analyzer discovery checks PascalCase entry points, excluding `build`, `bin`, and `obj`. Existing lowercase developer apps are outside this migration; pass an explicit file path to check one. Locate repository files from the runtime working directory, not `CallerFilePath`, which CI source mapping can rewrite.
